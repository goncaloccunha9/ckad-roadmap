2. Pod - The centre of everything

The Pod is the smallest unit you can create in Kubernetes. Everything else exists to create, configure, expose or monitor Pods.

A typical Pod that uses ALL the resources

  name: my-app
  namespace: default

  volumes:
  - name: data
    persistentVolumeClaim:                # ← PVC
      claimName: my-pvc
  nodeSelector:                           # ← Scheduling
    disktype: ssd

3. Workloads - Who creates Pods?

You rarely create a Pod directly. You use a controller that manages the lifecycle of Pods.

Hierarchy: Deployment → ReplicaSet → Pod

Deployment
↓ manages
ReplicaSet
↓ manages N replicas
Pod
↓ contains
Containers

Workload types

TypeWhen to useCreates
DeploymentStateless apps (web, API)ReplicaSet → Pods
StatefulSetStateful apps (DBs, queues)Pods with stable identity
DaemonSetOne Pod per node (logs, monitoring)1 Pod per node
JobA task that runs to completionPods (1+)
CronJobScheduled Jobs (cron)Jobs → Pods

How a Deployment creates Pods (selector + template)

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3                    # how many Pods to create
  selector:                      ─┐
    matchLabels:                  │  THESE 2 MUST
      app: web                    │  MATCH!
  template:                       │
    metadata:                     │
      labels:                    ─┘
        app: web                 ← labels of the created Pods
    spec:
      containers:
      - name: web
        image: nginx
⚠️ Exam gotcha

If selector.matchLabels does NOT match template.metadata.labels, the API server rejects the Deployment. Always check that they match.

CronJob - 3 nested levels of spec

apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup
spec:                            # ← CronJob spec
  schedule: "0 2 * * *"
  jobTemplate:
    spec:                        # ← Job spec
      template:
        spec:                    # ← Pod spec
          containers:
          - name: backup
            image: backup-tool
          restartPolicy: OnFailure

4. Configuration - ConfigMaps & Secrets

Where you store configuration and credentials for Pods. 3 ways to inject each one.

ConfigMap → Pod (3 paths)

ConfigMap (key=value pairs)
↓ Can be injected as:

1. envFrom (all keys)

envFrom:
- configMapRef:
    name: app-config

Injects ALL keys as env vars.

2. env (1 specific key)

env:
- name: APP_COLOR
  valueFrom:
    configMapKeyRef:
      name: app-config
      key: COLOR

For a single key, with optional renaming.

3. volume (files)

volumes:
- name: cfg
  configMap:
    name: app-config
# + volumeMount in the container

Each key becomes a file.

Secret → Pod (same 3 ways)

Identical to ConfigMap, but with secretRef / secretKeyRef, and the values are stored base64-encoded.

# envFrom
envFrom:
- secretRef:
    name: db-credentials

# env
env:
- name: DB_PASS
  valueFrom:
    secretKeyRef:
      name: db-credentials
      key: password

# volume
volumes:
- name: secret-vol
  secret:
    secretName: db-credentials

ConfigMapSecret
EncodingPlain textBase64 (not encryption!)
Typical useGeneral configurationPasswords, tokens, certs
Imperativekubectl create configmapkubectl create secret generic

5. Networking - How traffic reaches Pods

Pods have their own IPs, but they are ephemeral (they change when the Pod is replaced). That is why we use Services as a stable abstraction.

External traffic flow → Pod

🌍 User → Ingress → Service → Pod(s)

Ingress does HTTP routing • Service does load balancing (via selector → labels)

Service types

TypeReachable fromUse case
ClusterIP (default)Inside the clusterInternal communication (back-end ← API)
NodePortOutside, via node IP:port (30000-32767)Dev/testing
LoadBalancerInternet (cloud provider)Production
ExternalNameCNAME to an external serviceDNS mapping

Service ↔ Pod (the critical link is via labels)

# Pod
metadata:
  labels:
    app: web              ← the POD's label
    tier: frontend
spec:
  containers:
  - name: web
    image: nginx

# Service
spec:
  selector:
    app: web              ← MUST match the Pod's label!
  ports:
  - port: 80              # Service port
    targetPort: 80        # container port in the Pod
🚨 Most common mistake on the exam

A Service whose selector does NOT match the Pods' labels. Always check:

k get endpointslices -l kubernetes.io/service-name=SERVICE-NAME   # no endpoints → wrong selector!
k get endpoints SERVICE-NAME                                      # older API (deprecated since 1.33, still works)

Ingress - Advanced HTTP routing

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  rules:
  - host: mysite.com
    http:
      paths:
      - path: /wear              ← /wear goes to...
        pathType: Prefix
        backend:
          service:
            name: wear-service   ← this Service
            port:
              number: 80
      - path: /watch             ← /watch goes to...
        pathType: Prefix
        backend:
          service:
            name: watch-service  ← this other Service
            port:
              number: 80

NetworkPolicy - Pod-level firewall

By default, ALL Pods can talk to each other. A NetworkPolicy restricts that.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-policy
spec:
  podSelector:              ← WHICH Pods it applies to
    matchLabels:
      role: db
  policyTypes:              ← PLURAL!
  - Ingress
  ingress:
  - from:
    - podSelector:          ← WHO may connect in
        matchLabels:
          app: api
    ports:
    - protocol: TCP
      port: 3306
⚠️ AND vs OR (the CKAD gotcha)
# AND - 1 hyphen, 2 selectors together
from:
- podSelector: {...}
  namespaceSelector: {...}    # NO hyphen!

# OR - 2 separate hyphens
from:
- podSelector: {...}
- namespaceSelector: {...}    # WITH hyphen

6. Storage - How to persist data

When a Pod dies, it loses everything it wrote to its own disk. PV + PVC solves that.

Complete flow

Admin creates PV
↓
storage offering
available in the cluster
Developer creates PVC
→
request binds to a PV
PV
Pod
→
claimName
PVC

The 3 YAMLs together

# 1. PV (offers 100Mi)
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-log
spec:
  capacity:
    storage: 100Mi         ← capacity.storage (on the PV)
  accessModes:
  - ReadWriteMany          ← PLURAL!
  persistentVolumeReclaimPolicy: Retain
  hostPath:
    path: /pv/log

---
# 2. PVC (requests 50Mi)
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-log
spec:
  accessModes:
  - ReadWriteMany          ← must be compatible with the PV
  resources:
    requests:
      storage: 50Mi        ← resources.requests.storage (on the PVC, different from the PV!)

---
# 3. Pod that uses the PVC
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  containers:
  - name: app
    image: busybox
    volumeMounts:
    - name: log-storage    ← name of the VOLUME in the Pod
      mountPath: /var/log/app
  volumes:
  - name: log-storage
    persistentVolumeClaim:
      claimName: pvc-log   ← name of the PVC

Access Modes

ModeAbbrev.Meaning
ReadWriteOnceRWORead/write by a single node
ReadOnlyManyROXRead-only by many nodes
ReadWriteManyRWXRead/write by many nodes
ReadWriteOncePodRWOPRead/write by a single Pod

Volume types (in the Pod)

TypePersistenceTypical use
emptyDirLives as long as the PodSharing between containers in the same Pod
hostPathLives on the nodeAccess to the host's /var/log
persistentVolumeClaimPersistentDBs, production data
configMap / secretRead-onlyConfiguration files

StorageClass - Dynamic Provisioning

Instead of creating PVs manually, a StorageClass creates them automatically when a PVC is created.

StorageClass + PVC → PV created automatically → Pod

Complete YAML - SA + Role + RoleBinding

# 1. ServiceAccount
apiVersion: v1
kind: ServiceAccount
metadata:
  name: dev-sa
  namespace: default

---
# 2. Role (which verbs on which resources)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: default
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get"]

---
# 3. RoleBinding (links subjects to the Role)
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: default
subjects:
- kind: ServiceAccount
  name: dev-sa
  namespace: default       ← ALWAYS include!
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

Using the SA in a Pod

apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  serviceAccountName: dev-sa    ← this makes the Pod use that SA
  containers:
  - name: app
    image: my-app

Since Kubernetes 1.24, no token Secret is auto-created for a ServiceAccount. Pods get a short-lived projected token automatically; to get one manually, run k create token dev-sa.

Validating permissions

# Check MY permissions
k auth can-i list pods

# Check another SA's permissions (requires admin)
k auth can-i list pods --as=system:serviceaccount:default:dev-sa

# List ALL permissions
k auth can-i --list --as=system:serviceaccount:default:dev-sa

SecurityContext (on the Pod or Container)

spec:
  securityContext:          # POD level (affects all containers)
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
  containers:
  - name: app
    image: nginx
    securityContext:        # CONTAINER level (overrides)
      runAsUser: 2000       # this container runs as user 2000
      capabilities:
        add: ["SYS_TIME"]   # ← capabilities ONLY at container level!

8. Scheduling - How a Pod is placed on a Node

The kube-scheduler decides which node to place each Pod on, based on several rules.

Decision flow

Pod created → Pending → Scheduler evaluates → Pod assigned to Node → Running Scheduler criteria: 1. Resources (requests vs available) 2. NodeSelector (label matching) 3. NodeAffinity (advanced rules) 4. Taints/Tolerations (reject/accept) 5. Pod (Anti)Affinity (Pods together/apart)

NodeSelector - Simple

Node
label: disktype=ssd
↔
match
Pod
nodeSelector: disktype=ssd
# 1. Add a label to the node
k label nodes node-1 disktype=ssd

# 2. Pod
spec:
  nodeSelector:
    disktype: ssd

Taints (on the Node) + Tolerations (on the Pod)

Node
taint: special=true:NoSchedule
⛔
repels Pods without a toleration
Pod
# 1. Taint on the node
k taint nodes node-1 special=true:NoSchedule

# 2. Toleration on the Pod
spec:
  tolerations:
  - key: "special"
    operator: "Equal"
    value: "true"
    effect: "NoSchedule"
💡 Taints/Tolerations vs NodeSelector

Taints repel Pods (unless they tolerate the taint). NodeSelector attracts Pods. To fully dedicate a node, combine both (or a taint plus NodeAffinity).

NodeAffinity - More Flexible

spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: disktype
            operator: In           # In, NotIn, Exists, DoesNotExist
            values:
            - ssd
            - nvme

9. Observability - How to know it's OK

The 3 probe types

ProbeQuestionIf it fails
ReadinessIs it ready for traffic?Removed from endpoints (no traffic)
LivenessIs it alive?Container is restarted
StartupHas it started yet?Container is killed and restarted (for slow-starting apps)

Complete YAML with 3 probes

containers:
- name: app
  image: nginx
  ports:
  - containerPort: 80

  startupProbe:               # slow start (e.g. 5 min)
    httpGet:
      path: /healthz
      port: 80
    failureThreshold: 30
    periodSeconds: 10         # 30 × 10 = 300s = 5 min max

  livenessProbe:              # detect deadlocks
    httpGet:
      path: /healthz
      port: 80
    periodSeconds: 10

  readinessProbe:             # remove from traffic if not ready
    httpGet:
      path: /ready
      port: 80
    periodSeconds: 5

Pod Lifecycle

Pending → ContainerCreating → Running → (Succeeded | Failed) ↓ (Liveness probe failing?) ↓ Restart container ↓ CrashLoopBackOff (if it restarts too often)

Debug Toolkit

# Investigate one Pod

# Execute inside

10. Multi-container Patterns - initContainers & Sidecars

A Pod can have several containers that share networking and volumes. There are 2 kinds: initContainers (run first and exit) and sidecars/regular containers (run in parallel).

Anatomy of a multi-container Pod

Pod
↓ contains
initContainer 1 → runs + terminates
initContainer 2 → runs + terminates (sequential)
↓ then
main container sidecar → run in parallel

initContainers - "Setup before the show"

Containers that run to completion BEFORE the main containers start. They run sequentially (one at a time). If one fails, the Pod's restart policy applies and the app containers never start.

Use caseExample
Wait for a serviceWait for the DB to be ready before the app starts
Filesystem setupClone a Git repo into a shared volume
Downloading assetsFetch config/certificates from a registry
DB migrationsRun db migrate before the app
Volume permissionsRun chmod/chown on a mounted volume
apiVersion: v1
kind: Pod
metadata:
  name: web-with-init
spec:
  initContainers:                       # ← run FIRST, in order
  - name: wait-for-db
    image: busybox
    command: ['sh','-c','until nslookup db; do sleep 2; done']
  - name: clone-repo
    image: alpine/git
    command: ['git','clone','https://github.com/x/y','/data']
    volumeMounts:
    - name: shared
      mountPath: /data
  containers:                           # ← only start AFTER all init containers succeed
  - name: web
    image: nginx
    volumeMounts:
    - name: shared
      mountPath: /usr/share/nginx/html
  volumes:
  - name: shared
    emptyDir: {}
⚠️ Exam gotcha

initContainers run in ORDER, one at a time. If one fails, the Pod shows Init:CrashLoopBackOff. Debug with k logs <pod> -c <init-container-name>.

Sidecars - "Helper container"

A container that runs in parallel with the main container. It shares the network (localhost) and can share volumes. Used for auxiliary tasks.

PatternWhat it doesExample
SidecarExtends the main container's functionalityLog shipper, file sync, cache sync
AmbassadorProxy to external servicesEnvoy proxy, service mesh
AdapterNormalizes the app's outputConvert logs to Prometheus format

Classic example: log sidecar

apiVersion: v1
kind: Pod
metadata:
  name: web-with-logger
spec:
  containers:
  - name: web                           # ← main container
    image: nginx
    volumeMounts:
    - name: logs
      mountPath: /var/log/nginx

  - name: log-shipper                   # ← SIDECAR
    image: busybox
    command: ['sh','-c','tail -F /logs/access.log']
    volumeMounts:
    - name: logs
      mountPath: /logs                  # ← SAME volume, different paths
  volumes:
  - name: logs
    emptyDir: {}                        # ← shared between the 2

Communication between containers in the same Pod

2 ways to share data:

  • Network (localhost): container A reaches container B via localhost:<port>
  • Shared volume: an emptyDir mounted in both (paths may differ)

NATIVE sidecars (K8s 1.28+, stable in 1.33)

Kubernetes 1.28 introduced native sidecar containers: an entry in initContainers with restartPolicy: Always. The difference: it starts before the main containers but does not exit - it keeps running for the whole lifecycle of the Pod (and is shut down after the main containers). The feature is enabled by default since 1.29 and stable (GA) since 1.33.

spec:
  initContainers:
  - name: log-shipper
    image: busybox
    restartPolicy: Always               # ← the magic: makes it a NATIVE sidecar
    command: ['sh','-c','tail -F /logs/access.log']
  containers:
  - name: web
    image: nginx
💡 For the CKAD exam

Know both patterns: the traditional one (parallel containers in the containers: array) and the native sidecar (restartPolicy: Always on an init container). Use whichever the task asks for; the native form guarantees startup ordering and clean shutdown, which matters for Jobs.

Quick cheat sheet

CommandWhat it's for

k logs POD -c INIT_NAMELogs of an initContainer

11. Helm - Package Manager for Kubernetes

Helm is the "apt-get / npm" of Kubernetes. Instead of applying 20 YAML files by hand, you install a chart with 1 command.

3 fundamental concepts

TermMeaningAnalogy
ChartA package (templates + values) with everything needed to install an appA .deb / npm package
ReleaseAn installed instance of a chart in the cluster (has a name)A running application
RepositoryA collection of charts (HTTP URL)apt repo / npm registry

Typical Helm flow

Repositoryartifacthub.io / chart repos
↓ helm repo add
Charttemplates/ + values.yaml
↓ helm install + override values
Releaseresources created in the cluster
↓ generates
Deployment Service ConfigMap Secret

Essential commands (memorise!)

# Repositories
helm repo add podinfo https://stefanprodan.github.io/podinfo
helm repo update
helm repo list
helm search repo podinfo                     # search charts in added repos
helm search hub wordpress                    # search Artifact Hub

# Install
helm install my-release podinfo/podinfo      # release name + chart
helm install my-release ./local-chart        # local chart
helm install my-release podinfo/podinfo \
  --version 6.15.0 \                         # specific chart version
  --namespace prod --create-namespace \      # namespace
  --set image.tag=6.16.0 \                   # override 1 value
  -f my-values.yaml                          # override multiple values

# Lifecycle
helm list                                    # releases in the current namespace
helm list -A                                 # releases in all namespaces
helm status my-release                       # release status
helm get values my-release                   # show applied values
helm get manifest my-release                 # final generated YAML

# Upgrade / Rollback
helm upgrade my-release podinfo/podinfo --set replicaCount=5
helm history my-release                      # view revisions
helm rollback my-release 1                   # go back to revision 1
helm rollback my-release                     # go back to the previous revision

# Uninstall
helm uninstall my-release                    # remove everything
helm uninstall my-release --keep-history     # keep history

# Local templating (without installing)
helm template my-release ./chart             # render YAML without applying
helm install my-release ./chart --dry-run    # render and validate without installing

Structure of a Chart

my-chart/
├── Chart.yaml          # metadata (name, version, description)
├── values.yaml         # DEFAULT values (configurable)
├── templates/          # YAMLs with {{ .Values.X }} placeholders
│   ├── deployment.yaml
│   ├── service.yaml
│   └── _helpers.tpl    # reusable functions/helpers
├── charts/             # dependencies (subcharts)
└── README.md

Overriding values - 3 ways

# Way 1: inline --set (1-2 values)
helm install web podinfo/podinfo --set replicaCount=3

# Way 2: nested --set (with dots)
helm install web podinfo/podinfo \
  --set image.tag=6.16.0 \
  --set service.type=NodePort

# Way 3: -f YAML file (many values)
cat > my-values.yaml <<EOF
replicaCount: 3
image:
  tag: "6.16.0"
service:
  type: NodePort
EOF

helm install web podinfo/podinfo -f my-values.yaml

# COMBINING (precedence: --set > -f > default values.yaml)
helm install web podinfo/podinfo -f my-values.yaml --set replicaCount=5

Helm vs kubectl - when to use each

ScenarioTool
Installing a third-party app (nginx, postgres, prometheus)Helm
A complex custom app with 10+ resourcesHelm (build your own chart)
One-off simple resourceskubectl
Multiple environments (dev/staging/prod) with small differencesKustomize (preferred) or Helm
Dynamic templating with logicHelm
⚠️ Exam gotcha

Common mix-ups:

  • helm install <chart> ❌ → It must be helm install <RELEASE_NAME> <chart>
  • Forgetting --namespace → the release goes to default
  • --set uses dots for nested keys (image.tag), not slashes
  • Rollback uses the revision number, not the chart version

Exam cheat sheet

# Typical sequence for a CKAD Helm task:
helm repo add NAME URL                       # add repo
helm repo update                             # refresh index
helm search repo CHART                       # find the chart
helm install RELEASE REPO/CHART -n NS        # install
helm list -A                                 # confirm

helm uninstall RELEASE                       # remove

12. Docker & Container Images (CKAD focus)

Building container images falls under the "Application Design and Build" domain of the CKAD curriculum (define, build and modify container images). This section covers the essentials - nothing more, nothing less.

Where Docker fits in the Kubernetes stack

App code
↓ docker build + Dockerfile
Container Imagepackaged app (filesystem + metadata)
↓ docker push

Pod (Container Runtime pulls it)
💡 Important for CKAD

Kubernetes removed its built-in Docker Engine support (dockershim) in 1.24. Clusters now use a CRI runtime such as containerd or CRI-O. docker commands are for BUILD/TAG on your workstation; on cluster nodes, use crictl. The image format is the same (OCI), so images built with Docker run fine.

Essential Dockerfile (what matters for CKAD)

# Dockerfile for a simple Node.js app
FROM node:22-alpine                # ← base image
WORKDIR /app                       # ← set the working directory
COPY package*.json ./              # ← copy files from the host into the image
RUN npm ci --omit=dev              # ← run a command during build
COPY . .                           # ← copy the rest of the code
EXPOSE 3000                        # ← documents the port (metadata only!)
ENV NODE_ENV=production            # ← environment variable
USER node                          # ← non-root user (security!)
CMD ["node", "server.js"]          # ← default command at startup

CMD vs ENTRYPOINT (frequent gotcha!)

DirectiveBehaviourKubernetes equivalent
CMD ["a","b"]Default command/arguments - can be overriddenPod args:
ENTRYPOINT ["a"]Fixed executable - not easily overriddenPod command:
BothENTRYPOINT + CMD are concatenated at run timePod command + args
# Dockerfile with both:
ENTRYPOINT ["/bin/sh", "-c"]       # fixed executable
CMD ["echo hello"]                 # default argument

# At runtime:
# docker run image           → /bin/sh -c "echo hello"
# docker run image "ls -la"  → /bin/sh -c "ls -la"  (overrides CMD)

# In Kubernetes:
spec:
  containers:
  - image: my-image
    command: ["/bin/sh", "-c"]     # overrides ENTRYPOINT
    args: ["echo hello"]           # overrides CMD
⚠️ Exam gotcha

In Kubernetes, command: maps to ENTRYPOINT and args: maps to CMD. If you set command in the Pod, the image's ENTRYPOINT is IGNORED (not extended!), and so is the image's CMD unless you also set args.

Build & Tag - essential syntax

# Build from the Dockerfile in the current directory
docker build -t hello:1.2.3 .
                    │     │  │
                    │     │  └── build context (where the Dockerfile is)
                    │     └── tag (version)
                    └── image name

# Multiple tags in one build
docker build -t hello:1.2.3 -t hello:latest .

# Additional tag for an existing image
docker tag hello:1.2.3 myregistry.io/team/hello:1.2.3

# Build with a Dockerfile at another path
docker build -t hello:1.2.3 -f /path/to/Dockerfile.prod .

namespace/path — optional

myapp@sha256:abc123...             # by digest (immutable!)

Kubernetes ↔ Docker - how the cluster uses images

imagePullPolicy

ValueBehaviourWhen to use
AlwaysALWAYS pulls (checks the registry even if the image is local)Mutable tags (latest, dev)
IfNotPresentOnly pulls if the image is not present locallyImmutable tags (specific versions)
NeverNEVER pulls - only uses a local imageLocal dev with preloaded images
# Kubernetes defaults:
# Tag = "latest" OR omitted → Always
# Specific tag (e.g. 1.27)  → IfNotPresent

containers:
- name: web
  image: nginx:1.27
  imagePullPolicy: IfNotPresent       # ← explicit

Private registry - imagePullSecrets

# 1. Create a Secret with the registry credentials
k create secret docker-registry regcred \
  --docker-server=myregistry.io \
  --docker-username=user \
  --docker-password=PASSWORD \
  --docker-email=user@example.com

# 2. Reference it in the Pod
apiVersion: v1
kind: Pod
metadata:
  name: private-pod
spec:
  imagePullSecrets:                   # ← HERE
  - name: regcred
  containers:
  - name: app
    image: myregistry.io/team/myapp:1.0

# 3. Alternative: attach it to the ServiceAccount (all Pods using the SA get it)
k patch sa default -p '{"imagePullSecrets":[{"name":"regcred"}]}'

Multi-stage builds (good practice)

# Build phase + Runtime phase = small final image
FROM golang:1.24 AS builder
WORKDIR /src
COPY . .
RUN go build -o /app

FROM alpine:3.21                      # ← final image, no Go SDK
WORKDIR /
COPY --from=builder /app /app         # ← copies only the binary
EXPOSE 8080
ENTRYPOINT ["/app"]

# Result: final image ~10MB instead of ~800MB
